AZHottie Studio v1.36.0 — Returns, Exchanges & Creator Commission Settlement

What changed
- Customer Return Request page at /returns.php lets buyers submit an order reference, contact email, quantity and return/exchange reason. Public responses are deliberately generic, whether a reference exists or not, to prevent order enumeration. Email is encrypted at rest and available to authenticated staff only. Customer requests do NOT hold commissions, refund payments, or automatically authorize the return.
- The existing Commerce workspace adds Returns & Exchanges for administrators. Staff can intake a case, verify order ownership, authorize the request, physically receive goods, inspect items, and restock only verified resellable quantities. Restocking updates tracked inventory once with an audit record. Damaged goods cannot be marked restocked.
- Refund approval is a separate administrative state. No Stripe refund request is automatically issued; staff must execute a real refund in Stripe or the relevant cash/external provider and reconcile the order using the existing signed provider webhook/staff cash/manual evidence flow. The return case closes only when the order's refund ledger confirms the refund amount and an external reference is recorded. Stripe provider evidence continues to be signed and replay-protected.
- Like-for-like exchanges reserve stock only after inspection/approval and consume replacement inventory only on explicit staff dispatch with a genuine reference. No new purchase, attribution, shipping label or commission is manufactured by the exchange.
- Creator Payouts are now separate from estimated order commissions. A default 14-day post-payment holding window applies (private AZH_COMMISSION_HOLD_DAYS=7..90 can override; never below 7 days). Verified paid commissions are additionally held for unresolved authorized returns, Stripe disputes, unpaid or unfulfilled cash orders, or undelivered shipping orders. Manual external orders are clearly administrator-attested, not independently bank-verified.
- Administrators can draft and approve external payout batches using only eligible unallocated creator commissions. Draft allocations reserve balances and prevent duplicates; approval and final confirmation revalidate payment/return/delivery state and amounts. An externally completed payment can be marked Paid only after staff enters a unique transfer evidence reference and explicitly confirms the transfer. AZHottie does not send funds or initiate ACH, Stripe Connect, PayPal or cash payouts.
- A refund/dispute after a recorded payout can reduce earned commission below past paid allocations. That creates a visible overpayment liability and blocks all future payouts to that creator pending human reconciliation. This code does not automatically claw back money from creators.
- Creator/model accounts can view only their own estimated/eligible/held/recorded-paid balances and their own payout history. Administrator sees a staff-wide queue. Customer contact details, payment secrets and addresses are excluded from Agent Chat, notifications, Brain and creator balance views.
- Existing shared Agent bell, History, Chat, Brain and hourly cron receive return authorization/refund/exchange and payout events, outstanding approvals, overdue returns, unconfirmed transfer evidence and post-payout liabilities. Agents advise; no automatic payouts, returns approval, refund initiation or physical restocking occurs.
- Refund accounting fix: recording a full manual external refund now sets refunded merchandise and creator commission to zero. Stripe/cash refund accounting continues to depend on signed provider events or explicit staff confirmation, respectively.
- Schema version 41 → 42 adds return cases, immutable return audit, external payout batches and per-order allocation ledger with uniqueness and foreign keys. All existing product, live shopping, cash pickup, local delivery, carrier shipping, stock and creator attribution workflows remain intact.
- Public requests do not include tracking or automatic emails; store staff coordinate proof of purchase and physical logistics under applicable merchant return policies. Full/partial refund initiation, prepaid return labels, exchange variants, true bank transfers, tax filings, disbursement confirmation and account-level payouts are separate future provider capabilities.

Release verification
1. Back up full MySQL/SQLite database, storage/config.php, uploads, media and code; deploy the full application ZIP over application files. Do not rerun install.php.
2. Confirm schema version 42. Test the public return form against both a real and non-existent order reference; public response must not confirm order existence or reveal email/contact.
3. Test staff verification, status and revision conflicts, physically inspected restock, damaged-item rejection, same-item exchange and replacement dispatch.
4. Record a real Stripe TEST refund and verify the signed webhook updates the related order. Only then may staff close its approved return using evidence. Cash and manual external refunds require separate staff-recorded proof.
5. Check creator payouts: hold periods, open-return holds, delivered shipments, draft reservations, payment approvals, unique external evidence references, payout model isolation and post-payout refund liabilities.
6. Green CI on the final PR commit must include PHP/SQLite lifecycle, exact SQL constraints, JavaScript regressions, real Chrome desktop/mobile, and full ZIP integrity. Live MySQL, payment refund, physical stock and real external transfers remain distinct production verification gates.
