FINAL WORKFLOW AND IMPLEMENTATION NOTES
---------------------------------------
Project states: draft, active, completed, archived.
Shot states: active, closed, archived; distribution mode assigned or open.
Assignment states: assigned, accepted, submitted, changes_requested, approved,
 declined, cancelled. Submission states: draft, submitted, accepted, retake.

Contributor slots:
- Active member assignments count towards maxContributors (1..50), including
  submitted/approved work. Declined/cancelled assignments release their slot.
- The owning administrator may create a producer self-assignment. This does not
  consume a model/professional contributor slot. Uploaded footage retains the
  administrator as contributor and uploadedBy, including approved phone capture.
- assignmentCount includes producer work; contributorCount and slotsRemaining
  count only member slots. approvedAssignmentCount counts approved assignments;
  acceptedCount counts accepted submissions, not assignments.
- A project may have up to 200 shots. Role changes must not strand administrator
  close/archive controls; ineligible assignees cannot upload new footage.

Retake rounds:
- shot_assignments.current_round begins at zero. Draft uploads do not increment
  assignment revision or round, allowing multiple pending recordings to finish.
- submitAssignment tags all new drafts with submitted_round=current_round+1 and
  advances the assignment round. Older submissions and feedback are retained.
- reviewSubmission stores review_round=current assignment round. Any unresolved
  retake in that round makes changes_requested, including when a different take
  has already been accepted. The contributor can upload a replacement.
- A replacement submission advances the round. Old retakes stay in the history
  and do not block completion of the new round. Any still-unreviewed submission
  keeps submitted; when review is complete with accepted takes, state is approved.
- Reviewing other pending footage cannot erase a current-round retake. Reversing
  a retake to acceptance also works without deleting previous rounds.
- Reopen completed/closed work before requesting additional takes. Deadlines are
  advisory Phoenix times; lateness alone does not destroy or reject an upload.

Idempotency:
- Work mutation bodies may include requestId (8..160 letters/digits/_ . : -).
  Retries with the identical body and requestId return the current resource.
  Reusing the requestId for a different action or payload returns 409.
- work_requests stores actor, action, request hash and returned resource identity.
  Replayed responses are still checked against the caller's current permission.
- Assignment uniqueness is (shot_id,user_id). Open-shot claims are serialized
  under community.lock and the PDO transaction, including capacity checks.
- Scoped media clientToken is separate (16..160 letters/digits/_ . : -), with a
  unique (uploaded_by,client_token) upload receipt and assignment/token submission.
- Upload authorization binds assignment revision and shot revision. A changed
  brief, cancelled assignment, lost role, suspension or closed work rejects an
  unfinished upload. Completed acknowledgement retries do not duplicate footage.

Publication and source withdrawal:
- Production editor/export accepts reviewed, accepted, nonprivate, shortlisted
  submissions and eligible imported sources. Drafts and retakes stay out.
- Accepted-to-retake changes and cancellation of an assignment containing accepted
  footage unpublish that project's finished videos conservatively. Historical files
  and review records are retained.
- Archiving a project archives its backing interview, unpublishes its finished
  videos, disables the phone room, revokes connections and removes invites/signals.
- Archiving/deleting/withdrawing an ordinary imported source also unpublishes its
  destination projects. A finished video cannot be republished when its saved
  selectedTakeIds are no longer eligible. Restore never republishes automatically.
- Legacy API cannot delete/archive a project backing interview or delete production
  submissions. Editor state autosave still works with an unchanged modelId=null.

Transaction and schema integration:
- work-api.php POST: CSRF -> release session lock -> community.lock -> reload actor
  and password version -> PDO transaction -> mutate -> commit -> unlock.
- Media handlers: community.lock before uploads/admin-OWNER_ID.lock. Storage
  finalization and submission registration share/reuse a transaction as applicable.
- az_work_save_project and az_work_save_shot are transaction-neutral; the optional
  planner applies a reviewed proposal atomically under its own transaction.
- Schema 8 includes idempotent column checks for internal round counters. Schema 9
  handles optional AI configuration/proposals. Existing version 1.2 data is retained.

No test fixtures or account credentials are installed into the delivered storage.


V1.6 ROSTER ACCESS NOTES
-----------------------
- Roster membership grants discovery of active productions and eligible open
  shots. It does not assign shots, consume contributor slots, reveal another
  member's private direct shots/submissions, or grant administrator APIs.
- New direct assignments require membership, with the producer exception.
  Draft and active projects allow direct assignment; only active allows claim.
- My work.projects includes active included productions. My work.open requires
  current active membership. Existing assigned/history work is retained after
  removal, including uploads when the assignment, role and project permit them.
- Nonmanager shotCount includes only authorized shots. slotsRemaining and
  contributorCount are null for private direct shots and removed-member history;
  active open shots retain the capacity information needed to decide to claim.
- POST addMembers and removeMember use roster revision and optional requestId;
  see ROSTER_API.txt. Project revision and planner/editor fingerprints are not
  advanced by a membership-only change.
